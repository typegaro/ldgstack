# Manual flow (rare cases)

The orchestrator normally runs `tracker next` (see the spec-orchestrator skill). This is the full manual procedure the tracker automates, for cases `next` reports it cannot handle.

You are the parent. Run this in the main session; only the main session can delegate to subagents. Load `spec-cli` for spec history and `spec-tracker` for implementation records. Procedures (light path, audited spec edits, dependency guard, lanes, resuming, completion, releasing): [references/procedures.md](references/procedures.md).

Below, `spec` means `python3 <spec-cli skill base directory>/scripts/spec.py` and `tracker` means `python3 <spec-tracker skill base directory>/scripts/spec_tracker.py` (or the plugin's `bin/spec` and `bin/spec-tracker` wrappers). Spell the full command out in every Bash call: shell state doesn't persist between calls, and zsh doesn't word-split `$SPEC`.

```bash
spec validate | status | ready | next | waves | list | show <id> --effective | log <id> | preflight
spec edit <id> --from specs/.drafts/<file>.md --reason "..." [--user-decision "..."] --parent-confirmed
spec archive <id> --parent-confirmed
spec restore <id> --reason "..." --parent-confirmed
spec defer <id> --reason "..." --parent-confirmed   # park a draft; undefer <id> to resume
```

## Source of truth

- `specs/NNNN-<slug>.md` files are applied like migrations, in dependency order: a spec is ready when every spec it `depends_on` or `amends` is accepted (`spec ready`; `next` is the lowest ready id). `tracker init` refuses anything else without `--early` (see Parallel scheduling) or a recorded user decision. A `deferred` spec is skipped everywhere until `spec undefer`. `convention` specs bind every later unit. `decision` specs have no implementation: archive them once the user has accepted them. `- **L<n>**` (defined later) and `- **A<n>**` (accepted risk) items are not work: never implement them or write specs for them on your own; an implementer question that falls inside an open `L` item goes to the user. When the run ends, report the open ones (`spec later`, `spec risks`) with the remaining draft specs.
- An accepted spec is frozen. Changes arrive as new specs that amend or supersede it. Their tester also re-verifies the effective requirements of the amended spec.
- Specs never change to fit an implementation. Edits go through `spec edit` (audited, `--user-decision` for in-progress specs and conflict resolutions); the hook denies direct edits.
- The CLIs are the durable state. Never rely on conversation memory, and never edit their JSON or Markdown, or the plugin cache.

## Preflight (before the first delegation, and after any environment change)

`implementation/preflight.json` lists the commands every agent must be able to run, in each repository's real environment, e.g. `{"commands": ["cd be && nix develop -c go version", "cd fe && nix develop -c npx tsc --version"]}`. Create it with the user if missing; include the inspection CLI's `overview` once it exists. Run `spec preflight`, then `tracker toolkit verify` (`test-toolkit`). If preflight fails, stop and ask the user; never delegate into a broken environment. A failing or stale toolkit tool is repaired first (delegate `spec-workflow:spec-toolsmith`, no record needed, or ask the user).

## Loop

1. `validate`, `status`, `preflight`. Every tick, run `spec waves` and `tracker status` and schedule per Parallel scheduling. If no `convention` spec defines the developer inspection CLI, stop and create it with the user (`dev-inspection`, `write-specs`) before the first feature.
2. Take `next` (or another `startable` spec from `waves`). Read `show <id> --effective`, `log <id>`, every linked spec, the convention and decision specs, the spec's own `A` items, and project instructions.
3. If it has no record: `init` (leaves the record with the parent; `init --early` for a `plannable` spec). If a record exists, read `status` (including `pending`) and resume the role it needs.
4. **Derive requirements yourself, before any implementation.** `requirement import <feature>` (amended targets included; `--exclude-amended` skips them), read its warnings, then add what import can't see: prose rules without an ID (`requirement add --spec-ref "<id>:<section>"`), touched requirements not cited as `<id>:R<n>`, and sharper `--verification` where a bullet isn't observable.
5. **Plan.** `handoff --to planner` (creates its read-only lane; `--parent-confirmed` also recalls an executor that has implemented nothing), delegate `spec-workflow:spec-planner`; it stores the plan (`plan add`) and hands back (`plan_ready`). Read `plan show <feature>`; send obvious gaps back with `handoff --to planner --remaining "<gap>"`. Required for more than 3 requirements or more than one area; skip only with `handoff --to implementer --parent-confirmed --reason "..."`.
6. **Execute.** Worktree mode: `worktree create <feature> --parent-confirmed` first (see Worktrees). `handoff --to implementer`, `assign <feature> --role implementer --from-plan [--batch N] --parent-confirmed`, then `brief --role implementer --batch 1` to a `spec-workflow:spec-implementer` (the executor). Plans have 3–5 batches; give each to a **fresh executor** with `brief --batch N+1` (it reissues the assignment once the earlier agent claimed it; `--fresh` forces a new one); never resume one executor past ~200k context. Batches the plan marks `**Parallel:** yes` (disjoint lanes, e.g. be and fe) run together: `assign --from-plan --batch N --parallel` per batch, then `brief --batch N` each. Each executor ends its batch with `join <feature> --assignment <ID>` (its brief's Next command), which frees only its lane; a handoff is refused while sibling lanes are active. The last executor (or the integration batch) hands off. Executors run focused tests for their batch; the full suite runs once, in the test round. The record carries state between them; resuming is for small follow-ups, short fixes, and a retest by the same tester. Testability requirements are executor batches, never toolsmith work. The final batch opens the PR (`tracker pr open`, worktree mode; it hands off to review) or hands off to review.
7. For every delegation, paste the `tracker brief <feature> --role <role>` output **verbatim** as the prompt, appending only extra context below it (never another agent's report for a verifier). Never send a pointer to a brief ("run brief ...", a file path); a hook warns when the marker is missing. `brief` refuses an unbatched implementer brief for more than 10 requirements, more than 2 areas, or a multi-batch plan.
8. **Questions.** On `needs_answer` (`status` shows `open_questions`): answer from the spec, plan, and code with `answer <feature> --text "..."` (back to the asker; resume it with SendMessage and the answer). Design questions, or a wrong plan: `answer --replan` (planner, then `assign --from-plan` again). Ask the user only for decisions listed below.
9. On `ready_for_verify` (worktree mode, the default `verify: parallel`): the writer's PR put the reviewer and the tester on the same patch at once. Brief a fresh `spec-workflow:spec-reviewer` (`brief --role reviewer`) and a fresh `spec-workflow:spec-tester` (`brief --role tester`) together; each passes `--as reviewer|tester` on `check add`, `bug add`, and its final `handoff --to parent`, and the last one returns the record. If the test slot is busy, start the reviewer now and the tester when `queue wait test` exits. On `ready_for_review` (sequential mode, or a tool gap kept the tester out): a fresh reviewer. On `ready_for_test`: a fresh tester (handoff creates its read-only lane). In worktree mode all of them go through queues (Parallel scheduling): the record joins the review and test queues by itself; start `tracker queue wait review|test` as a background Bash command and brief the item it prints when it exits. `brief` refuses an item that has no slot yet and names the wait command. Every verdict records the branch's patch id; acceptance needs a passing review and test of the patch that would land, so a clean merge of main keeps them and any later commit needs them again.
10. On `needs_tooling`: `handoff --to toolsmith`, delegate `spec-workflow:spec-toolsmith`. When a test round leaves both bugs and tool gaps, run them in parallel: `handoff --to fixer`, assign the fixer, then `assign --role toolsmith --paths <disjoint> --alongside --parent-confirmed` and brief both; the toolsmith ends with `join`, and the fixer's handoff waits for it. when it hands back, resume the tester that recorded the gaps (SendMessage; a fresh tester for reviewer-recorded gaps). To skip a gap, ask the user and `tool-gap defer` it. If a toolkit requirement was routed to the toolsmith anyway, record its gap yourself (`tool-gap add ... --parent-confirmed`), then `requirement implemented --evidence-from toolkit-<name> --parent-confirmed` after it lands.
11. On `bugs_found`: only a finding proven by a run blocks. `bug add --unproven` low or medium findings and `--preexisting` ones (main already has them) are filed as follow-ups automatically; an unproven high or critical finding stays open: get it proven (resume its finder or run `interrogate`) before assigning a fixer, or close it with the user's decision. Low bugs (medium with the user's decision) that don't break a requirement go to `bug follow-up <feature> <BUG> --reason "..." --parent-confirmed` instead of a fix round. `bug assign` the rest, `handoff --to fixer`, delegate `spec-workflow:spec-fixer` (about 4 bugs or one area per fixer); fixer work advances the implementation generation. Review each fix by risk tier (`tracker risk <feature> high|normal`, set at init: high for security, data, migration, or concurrency): **high**, a fresh `spec-workflow:spec-reviewer`; **normal**, resume the reviewer that found the bugs, scoped to the fix diff. **Light rounds:** a fix of only low bugs with a small diff (or tests, config, or docs only) that touches nothing sensitive goes straight to retest (`pr open --light` / `handoff --to tester --light`; the tracker measures the diff, refuses otherwise, and records check `rereview-skipped`). Then retest by resuming the tester that recorded the bugs or a fresh tester (always for reviewer-found bugs). A re-review that finds only a new low bug in an otherwise good fix: `bug follow-up` it (no user decision needed) instead of another round. A normal (non-light) fix round ends in `pr open`, which starts parallel verify again: both roles check only the fix diff (`git diff <fix-round base>..HEAD`, in the brief) plus their regression checks. Repeat until every bug is verified, closed with a user decision, or a follow-up.
12. A reported missing requirement: check it against the spec; if real, `requirement add` (`--parent-confirmed` if the record is with another role) and send the record back to the implementer. After a passed review, an implementer that only implements added requirements may hand off straight to the tester; send a fresh reviewer when they change security, data, or lifecycle behavior.
13. On `blocked`: resolve what the spec answers (`blocker resolve --parent-confirmed`); otherwise stop and ask the user. `not_run` checks don't block review or retest; get them run, or a user waiver, before acceptance.
14. `tracker gate <feature> acceptance`. Worktree mode: `tracker queue add merge <feature> --parent-confirmed`, then `tracker queue run merge --parent-confirmed` (one item per run; `queue wait merge` in the background when another merge runs). It merges main into the spec branch, runs the fast CI tier and `hooks.pre_merge` on the result, fast-forwards main, archives the record and the spec, removes the checkouts, re-checks every open PR against the new main, and runs `hooks.post_merge`. A failed CI command is re-run once (a pass is recorded as flaky in the `ci-fast` evidence and `flaky` in the result). A conflict or a CI failure returns the record to the fixer with an assigned bug: `assign --role fixer --from-plan` and brief it. When the failed command also fails on main, the result is `main_red`: no bug is filed, the item keeps its place, and main must be fixed first (its own spec, or a fix with the user's decision); then run the queue again. A CI failure that is a flake unrelated to the spec: `handoff --to parent`, then with the user's decision `bug close <BUG> --reason "..." --user-decision "..." --parent-confirmed`; while the branch is unchanged this restores the reviewed and tested generation (`restored` names the next commands: `ci run`, `queue add merge`); an agent's conflict resolution needs a fresh focused review before acceptance. Then `spec preflight` (on main). Without worktrees: `tracker archive <feature> --parent-confirmed && spec archive <id> --parent-confirmed` (both recheck their gates).
15. Continue without asking until no numbered spec remains; then follow Completion in the procedures.

## Supervision

Judge agents by side effects (claims, commits, tracker writes), never by their status text.

- **Stuck agents.** Every tick, run `tracker stuck`: it lists active assignments with no claim, record write, or commit past twice their role's usual run time (learned from past assignments). Probe a stuck agent once; then replace it at once with a fresh brief, by cause: after a context or usage limit, a smaller scope (one batch, fewer bugs); after a dropped connection or a crash, the same brief; after a tool error, another model (Agent `model`). After two retries, drop the unit and replan around it (`answer --replan` or `handoff --to planner`). A stopped agent that returns late: compare its result with the record's current state and hand any unique findings to a fresh agent.
- **Fresh over resumed.** Give new work to a fresh agent whose brief carries the consolidated scope (the brief, later directives, the earlier report's facts that aren't verdicts). Resume an agent only when the work needs state that lives in it (its uncommitted checkout, a running process) or for the retest and normal-risk fix review allowed under Independence; resumed agents silently drop directives.
- **Start with one unit.** After a plugin upgrade, a change to briefs or skills, or a new kind of spec, run one spec end to end before fanning out the rest, so a flaw costs one agent instead of five.
- **Audit tick.** In a long autonomous run, schedule a wake-up about every hour (ScheduleWakeup or `/loop`): reread this skill, run `tracker status`, `tracker stuck`, and `tracker queue status`, fix drift (an unrecorded decision, an idle queue item, a lane nobody holds), replace stuck agents, and post to the user only when something they'd care about changed. A tick that changed nothing stays quiet.
- **Decision log.** Every call you make alone on the user's behalf (a default you picked, a follow-up you deferred, a replan, a dropped unit) gets `tracker decision add --feature F --decision "..." --why "..." --evidence "<check, commit, file:line>"`. A call only the user can make (Decisions that belong to the user) that arrives while they are away becomes `tracker decision add --waiting --pick "..." --risk "..."`; keep working on everything it doesn't block. Their answer goes in with `tracker decision resolve D-NNN --answer "<their words>"` and into the command's `--user-decision`. The dashboard shows waiting calls and stuck agents under "Waiting on you".
- **Prototype before asking.** A question that running something can answer (behavior, timing, layout, output, performance) is not the user's: settle it with the `prototype` skill and log the decision. Ask only for product or preference calls no experiment settles.
- **Restate the goal.** Every brief opens with the spec's goal; your own first message on a task, and the final report, restate the user's goal and the smallest change you expect to meet it.
- **Catching the user up.** When the user returns or asks where things stand, use `catch-up`: what changed in plain words, then each waiting call with your pick, evidence, and risk.

## Quality skills

Briefs name these; agents load them by name. `engineering-principles` (cited by name in handoffs, bugs, and reviews), `deslop` and `no-comments` (writers run both before `pr open`), `tdd` (fixers, when a cheap test path exists), `typescript-practices` and `go-practices` (by file type), `unslop` and `technical-writing` (handoffs, bug reports, PR descriptions, docs). For hard calls: `how` and `why` (grounding), `architect` with `arena` (the planner on high-risk or one-way-door specs: two structurally different sketches), `interrogate` (the reviewer on high-risk specs, and to prove a contested finding), `blast-radius` (reviews of merge resolutions and small risky diffs), `swarm` (coverage checks and verify lanes), `verification-map` (testers drive features from the map and extend it), `formal-verification` (concurrency, lease, queue, and retry properties on high-risk specs), `benchmark-checklist` (any measured number), `correct` (after a retro, turn repeated corrections into checks), `sharpen` (vague requests, before `write-specs`).

## Model tiers and escalation

Use capabilities, not provider-specific names: planner and reviewer use a **deep-reasoning tier**; implementer (executor), fixer, tester, and toolsmith use an **efficient execution tier**. This Claude plugin maps those tiers to `opus` and `sonnet` in agent frontmatter. OpenAI equivalents include GPT-5.6 Terra with `high`/`xhigh` reasoning and GPT-5.6 Sol with `medium`/`high` reasoning. Treat these as examples and map the tiers to the models available in the host.

- An executor that fails the same gate or check twice: `handoff --to parent`, then `handoff --to planner --remaining "<failure>"` (or `answer --replan`).
- A fixer whose fix fails retest: rerun it on the deep-reasoning tier (for Claude, Agent `model: "opus"`; for OpenAI, for example GPT-5.6 Terra at `high`).
- High-risk specs (security, data migration, concurrency): after the normal tester passes, run one extra `spec-tester` pass on the deep-reasoning tier, scoped to edge cases.
- On a retest, `check add` with the failed check's exact name supersedes it; the brief lists those names. A gate error names the role that must re-record a check and the handoff command; never attest a reviewer's or tester's check as the parent.

## Parallel scheduling

Prefer parallel work whenever the dependency graph and lanes allow it. `spec waves` returns `startable` (all `depends_on`/`amends` accepted), `plannable` (draft, every unaccepted dependency is in progress or startable; `blocked_on` lists them), topological `waves`, and `deferred` (ignored).

- **Plan ahead.** Launch planners for `plannable` specs while their dependencies are implemented or reviewed: `tracker init <spec> --early` stores `early` and `blocked_on`, then derive requirements and plan as usual. Planners mark each batch `**Requires:** <ids>|none`.
- **Early batches.** In an early record, `assign --from-plan` and `brief --batch N` refuse a batch whose `Requires` names an unaccepted spec (no line = all of `blocked_on`). Run batches marked `Requires: none` at once; run the rest once those specs are accepted. `gate acceptance` and `archive` wait for all of `blocked_on`. Overrides need `--parent-confirmed --user-decision`.
- **Parallel executors.** Run executors for `startable` specs, and for early `Requires: none` batches, together. In worktree mode specs never share files, so overlap only predicts merge conflicts (`assign` reports `merge_risk`). Without worktrees, run `tracker overlap --plans` first: any pair it reports would edit the same files, so serialize those or narrow the plans. Keep `be/` and `fe/` in separate lanes.
- **Fresh agents per batch.** Long runs cost most (17 runs past 250k context in the 0.8.3 retro): a fresh executor per plan batch (or 2 small batches) and a fresh fixer per ~4 bugs or one area. Resume an agent only for a small follow-up, a short fix, or a retest by the tester that found the bugs.
- **Shared paths across specs.** When `assign` refuses an overlap, use the narrow globs its error lists, or `assign <feature> --role <role> --carve <glob> --from <ASSIGNMENT> --parent-confirmed` to take a narrow glob out of the other spec's active lane (both lanes record it; the other agent's writes there warn, and its next brief shows the carve-out). Tell the other agent with SendMessage if it is running.
- **Pipeline roles.** While spec A is in review or test, spec B's executor runs. Two agents work on one spec only as `--parallel` executors or a toolsmith `--alongside` the fixer; never combine specs in one agent.
- **Concurrency cap.** Default at most 2 executors/fixers plus 1 deep-tier agent (planner/reviewer/deep tester) at a time; the user may change it. After a usage-limit stop, lower the cap by one and resume the stopped agents with SendMessage instead of restarting them. Stagger starts.
- **Pipeline (worktree mode): open PR → review queue → test queue → merge queue.** Writers end with `tracker pr open` (commits on the branch, no conflict with main, project PR checks, fast CI; a refusal keeps the record with the writer). Records join the review queue on `ready_for_review` and the test queue on `ready_for_test`/`ready_for_retest` (a retest goes first). Each queue has slots per resource class (workspace.json `slots`: review 2, test `test_slots` or 1, merge 1 by default; `assign --role tester --slot-class browser` picks a class). A class can be `auto` (the cost of one run in memory and CPUs, with `min` and `max`): it grants another slot only while the machine has room after the `capacity` reserve, so parallel testing grows and shrinks with the machine. `tracker capacity` shows free memory, load, and how many more runs each auto class allows now. An agent's `claim` holds the slot, its handoff frees it, and a dead agent's slot frees after the `lease` (default 2h).
- **Wait, don't poll.** Keep one background `tracker queue wait <queue>` per queue with waiting items (`--feature F` for one record); its exit is the wake-up. `tracker queue status` and `tracker pr status` show the whole picture. After each merge, `queue run merge` lists the open PRs that now conflict with main (`conflicting_prs`); their queue items wait, and `tracker pr return <feature> --parent-confirmed` sends each to the fixer before review or test. Agents that test get isolated databases and ports (`env.isolate`); nothing runs the server against the dev database. Writers are in no queue: an executor or fixer that runs a stack E2E wraps it in `tracker queue hold test --feature F --class stack --run "<command>"`, which waits for a slot of that class, holds it while the command runs, and frees it.
- **Worktrees** (`implementation/workspace.json`, procedures › Worktree mode). Each code repo is a folder of checkouts: `<repo>/main` is accepted code, `<repo>/<branch>` is one spec's. A dependent spec starts from its dependency's branch. Merge through the merge queue, one spec at a time; a conflict returns the record to the fixer, who merges main into the branch and opens the PR again. Dev deploys come only from `<repo>/main` (`hooks.post_merge`).
- **Hygiene.** Each agent gets its own scratch subdir (`$SCRATCH/<role>-<assignment>/`). The parent serializes tracker writes per record (one `tracker` call at a time for a feature) and handles each agent's report as it arrives.
- Lanes stay enforced: `assign` refuses overlapping paths and the hook denies writes outside a lane; run `tracker overlap --depth 2` after each implementer or fixer round. A blocked spec holds only its dependents.

## Independence

- **Never** pass the implementer's or fixer's report, rationale, or summary to the reviewer or tester. Briefs never show the plan to testers; reviewers get a pointer to compare against it.
- Use a fresh agent for every first review and test round. Only a retest may resume the tester that found the bugs, and only a normal-risk fix review the reviewer that found them.
- Run verifiers on a different model from the writer when the host allows it (the Agent tool's `model` parameter; in OpenCode, another provider). The reviewer is on the deep tier and the writers on the efficient tier by default, so that holds for review; for high-risk specs give the tester the other model too.
- Only a finding a run proves blocks a merge: a bug a user would hit, a failed gate, or a doc the change made wrong. Everything else is a follow-up. A problem main already has doesn't block unless the change copies it or newly reaches it (`bug add --preexisting`).
- CI results (`ci-fast`) are the writer's evidence. They never replace the reviewer or the tester.

## Decisions that belong to the user

Don't judge your own exceptions. Use AskUserQuestion and record the answer verbatim in `--user-decision` for: waiving a check (a missing toolchain or service is never a reason), closing a bug as not a bug, resolving a blocker the spec doesn't answer, deferring a tool gap, starting a spec before its dependencies are accepted (other than `--early`), running an early batch before its required specs are accepted, and editing an in-progress spec or resolving a conflict between specs (`spec edit`).

## Stop and ask the user when

- Specs contradict each other, or a material product, security, data, lifecycle, or compatibility decision is missing.
- Specified behavior is impossible or unsafe as written.
- Preflight fails, or required external access has no deterministic local substitute and the toolsmith cannot build one.
- Repeated fix attempts make no progress.

Give one consolidated report: exact references, evidence, impact, options, and a recommendation. Never edit specs on your own judgment, accept risks, skip the blocked spec, or continue dependent work.
